# 预选档位与锁票研究

核对日期：2026-10-08。当前开发中的 v0.1.6 已识别实测排队页面，尚未启用自动选票、选座或锁票。

## 希望实现的行为

在正常通过官方认证、验证和排队之后，读取该商品实际场次的可售项，只考虑用户预选的档位与数量。普通票可以选择该档位中符合座区偏好的任意可售座位；允许分散座位。Play＆Stay 则需要匹配酒店、房型、人数组合与套餐份数。首选确认为售罄后，才按购票优先顺序考虑下一选择。

选中或高亮只是本地选择。只有正式售票页面或正常响应明确确认库存已被当前会话锁定，才可以记录锁定成功。锁定成功后停止尝试其他选择。响应不明、部分成功或释放未确认时暂停接管。

## 本轮普通票实际流程

按用户最新指定，研究目标已切换为 [JEONGHAN × JOSHUA 普通票](https://world.nol.com/zh-CN/ticket/places/26001167/products/26013793)，商品 26013793、场馆 26001167。此前 TXT 和 JJ 酒店套餐只作为入口参照。

2026-10-08 晚在用户当前 Edge 中完成了以下观察：

1. 官方商品页显示 Assigned Seat / General，公开票价 143,000 韩元；预约按钮为“先行订购”。这表示当前提供会员预售入口，不代表账号已有资格，也不代表有库存。
2. 关闭商品公告后，手动点击一次官网“先行订购”。按钮随后禁用，页面在当前标签页正常跳转至 tickets.interpark.com 的 /gates/partner。
3. Edge 显示 ERR_CONNECTION_TIMED_OUT，未加载排队或选票页面。此前 TXT、JJ 酒店套餐同一售票域名也超时；没有通过改商品取得后段页面。

这验证了官网按钮的正常同标签跳转行为，**不等于扩展入场 API 已在真实账号中通过验收**。未获得正式场次 ID、实时座位、锁座请求或响应，没有锁票、创建订单或付款。跳转中的入场凭据未保存进源码、诊断或本文。

v0.1.5 针对本轮暴露的入口状态问题完善错误保留和恢复提示，并识别活动购票标签的官方主页面导航错误。它不会修复售票域名的网络连接，也没有开启未经观察的选座与锁座动作。要继续适配，需要该 Edge 会话能正常进入正式选座页；后续按用户指定的普通票流程采样。

## 网络恢复与实际排队

用户更换代理后，当前 Edge 已正常进入该普通票的官方 /waiting 页面。本轮沿用这一现有标签观察，没有刷新、重新进入或另建队列。页面实际显示商品全名、我的等候顺位和当前等候人数；顺位持续下降。

页面“订购率”的说明指已完成付款的门票比例，正在付款的门票还可能占用余量。因此该百分比不表示可选择的座位数量。页面还提示进入预约页后有选座时限，刷新或重新连接会重置排队顺位。

已观察并适配该版本桌面繁中排队 DOM：商品全名来自 Wait_goodsName__Sjp96，顺位来自 StatusBox_mainText__9gJXJ 的 h3 / strong，“現在等候人數”从对应 StatusBox_row__rN2QG 的右列读取。适配要求官方精确路径、已观察结构、唯一有效数字以及任务商品全名匹配；结构、语言或商品不符合时交人工检查。不读取或保存队列 URL 参数，也不将“订购率”解析为余票。

公开排队脚本确认，正常入场依赖服务器返回 oneStopUrl，再由网站调用 document.location.replace 自动跳转；顺位为零本身不能代替正式预约页面的加载结果。公开源：[排队页面脚本](https://tickets.interpark.com/waiting/_next/static/chunks/pages/index-68a114581efc8d15.js)、[共享脚本](https://tickets.interpark.com/waiting/_next/static/chunks/pages/_app-6db3b888368367a0.js)。本轮只匿名读取公开静态脚本，没有调用或重放任何排队接口。实际后段地址已在正常自动跳转后观察到，见下节。

v0.1.6 将“已在实际页面观察到队列”单独记录为 queueObserved，不据此宣称入场 API 回执成功。与任务匹配的当前队列可解除此前网络 / 回执不明确的观察阻碍，恢复时只继续观察。晚到的 API 回执不能覆盖已确认队列，也不会重复提交入场。

目前 115 项 Node 测试通过；Edge / Chrome 各 6 项队列隔离检查通过，验证数字更新、错商品检查及回执不明确时的观察恢复。测试使用无参数的本机拦截页面和脱敏 DOM 夹具，没有进入真实队列、选座、锁票或订单。

## 已进入正式选场与选座页

沿用上述队列，网站正常自动跳转至 `https://tickets.interpark.com/onestop/schedule`，没有刷新或再次请求入场。该页没有 iframe，日历默认选中 2026-10-30，时间行显示 7:00 PM；10 月 31 日及 11 月 1 日按钮也可用。这里只记录控件可用状态，不能据此判断这些场次还有余票。

为查看后段，点击一次官网“下一步”，进入同标签 `/onestop/seat`。商品全名与 JJ 普通票一致，当前场次显示 `2026.10.30(周五) 7:00 PM`，页面开始显示实际选座倒计时、座区图及“完成選擇”按钮。按钮在没有选择时禁用；图片验证码弹层提示“輸入文字後才能選擇座位”，已交由本人完成。默认场次不作为实验购买配置，没有选择座位、确认选择、锁票、订单或付款动作。

本轮实际观察的 DOM 包括 `SubHeader_headerTitle___LjIv` 商品标题、`SubHeader_scheduleDate__UaD4B` 场次显示、`ModalCaptchaText_layerWrap__jn1bV` 验证码层和 `SeatMap_blockImg__QQUF7` 座区图。图来自官方 SVG：[场馆底图](https://ent-ticketimage.interparkcdn.net/svg/26001167/ea91e9b960c8466bad10fea7bf8a44af.svg)、[座区图](https://ent-ticketimage.interparkcdn.net/svg/26001167/087dd34c78914d7c972c56fc356b0e3b.svg)。这些图不等于实时可售座位数据。页面脚本为官方新 OneStop 前端，而非此前未取得的旧 Global ASP 页面。

v0.1.6 对这一个已实测的商品、场次和布局增加只读页面识别：核对任务商品 / 场馆、完整标题、可见场次与地图，提示本人完成可见验证码。更换商品、场次或布局仍交人工检查，不自动操作验证码或座位。进一步匿名分析实际页面加载的公开脚本，已定位临时预选和确认接口；方法、异常和前端计时见 [OneStop 技术研究](onestop-flow-research.md)。这仍不能替代真实成功回执。

本轮验证码没有完成，官网最终显示可见 modal：“10分钟的座位选择时间已超过”“请重新开始预订”，并移除地图。实际结构为 `div.nds-e-dialog__container[role="dialog"][aria-modal="true"]`，包含 `nds-e-dialog__title`、`nds-e-dialog__description` 及“确定”按钮。v0.1.6 在核对商品与场次后先检查该超时层，避免把底下尚存的验证码当作可继续的状态；不点击确定、不自动重启。没有进行选座、锁票或订单实验。

## 需要取得的实际证据

1. 正常入场后的商品、场馆、日期、时间和实际场次编号；观察 iframe 或新窗口是否承载选票控件。
2. 普通票的档位、座区、座位 ID 与实时可售状态；套餐的档位、人数与“份数”的实际含义。不得用日期范围、预售编号或价格档编号代替场次 / 座位 ID。
3. 正常选票并完成选择后，网站怎样向服务器提交；售罄、竞争冲突及部分成功的实际返回。
4. 官方如何确认当前会话已锁定，实际锁定了哪些票 / 套餐、数量，以及是否提供有效期或释放方式。网站未提供的信息保持未知。

下一步是在当前正式选座页完成本人验证码后，观察可售座位控件。真实锁定实验需要明确实验场次、档位和数量；沿正常官方流程验证，不执行付款。

## 本次代码修正与范围

v0.1.4 修复普通票选择校验遗漏档位的问题：配置中的 `seatGrade`、`priceGrade` 只要非空，候选都必须分别匹配；错档位、缺少已要求的档位不能通过，价格更低也不能越过限制。未选档位时保持原有座区偏好语义。

新增两项测试，验证错档位不能参与排序或通过订单校验，以及未选 / 单独选择档位编号的行为。现有套餐匹配、优先顺序和无价格上限规则保持不变。

这仍是纯函数校验。当前候选模型是一组完整购票选择，尚未实现从逐座实时库存组合出指定数量的座位，也未接入任何锁座请求。扩展进入未适配的正式售票页面时仍会提示人工接管。
