# NOL 公演助手

个人使用的 Chrome / Edge Manifest V3 扩展，当前版本 **v0.1.5**。

长期目标是覆盖 NOL World 的完整购票过程：开售值守 → 官方验证与排队 → 场次和套餐 / 座位选择 → 座位或套餐锁定 → 填写资料 → 创建订单 → 支付准备，并探索可选的支付自动化。

**目前交付的是入口辅助版本，自动操作只到官方购票入口。** 场次选择、选座、座位锁定、资料填写、创建订单、支付页面识别和付款均未接入真实售票流程。本 README 的后续路线是开发计划，不代表这些功能已经实现。

粘贴商品链接后，当前版本可自动读取公开商品、票档和开售时间，保存联系人、数量及购票优先顺序。开售时间只使用官方 `salesinfo` 接口，不允许手动填写；保存和启动任务均重新读取，值守期间每分钟复核。普通开售与会员预售分别读取，同时显示北京时间和韩国时间；多个有效预售窗口必须明确选择对应类型。**选票不设价格上限**，旧任务的预算也不再限制选择。

到官方开售时间后，扩展在当前商品页使用浏览器正常同源会话读取账号票务状态、完成可交互的官方 Turnstile 验证，然后单次调用 `/api/users/enter/token`，沿官方 partner gate 继续。验证码由本人完成，没有 DOM 点击兜底或重复接口提交。入场 API 的客户端接线和模拟流程已经核对，**真实登录、验证及排队入场尚未实测**。

## 后续开发路线

开发按下表顺序推进。每个阶段先在真实官方页面观察和适配，再进行可重复的模拟验证与限定范围的真实验收；通过前一阶段后再启用下一阶段自动操作。

| 阶段 | 开发内容 | 完成与启用标准 |
|---|---|---|
| 1. 登录后流程观察 | 优先研究用户指定的 JEONGHAN × JOSHUA 普通票，再单独核对 Play＆Stay；记录实际页面、iframe / 新窗口、跳转顺序和控件 | 取得正常登录后页面证据；选择器、字段和状态均来自实际页面，未知页面停下接管 |
| 2. 官方验证与排队衔接 | 检查登录和会员资格；识别公告、验证码、排队、入场和会话失效；人工完成验证后恢复任务 | 正常官方流程中能够继续，验证中不重复点击、不新开竞争队列；会话失效或浏览器重启后要求重新检查 |
| 3. 场次与酒店套餐选择 | 读取实际日期、时间、场次 ID；按第一选择、第二选择顺序匹配酒店、房型、人数组合或票档 | 用页面实际 ID 操作；售罄首选才转向下一选择，不误选商品、日期、人数或套餐份数；价格不改变显式优先顺序 |
| 4. 普通票座区与座位选择 | 读取已适配选座页的区域、排号、座号及可选状态；支持座区顺序和分散座位 | 能把偏好映射到实际座区 / 座位；同座区再比较价格；库存变化、选不到足够数量或页面变化时明确处理 |
| 5. 座位 / 套餐锁定 | 在官方流程中确认库存锁定；识别正式页面或正常响应所提供的锁定结果、对应席位 / 套餐和有效期；处理部分成功、冲突及到期 | **按钮点击或座位高亮不能视作锁定成功**；必须取得官方确认。锁定未确认时暂停；确认已有锁定或订单后不盲目切换选择。网站未提供的锁定编号或有效期不编造 |
| 6. 资料填写和未支付订单 | 按页面实际字段填写本机联系人；核对商品、场次、票数、席位 / 套餐和含费总额；防重复提交，并查证提交结果 | 完成一次已授权的未支付订单实验并停在付款前；提交超时或结果不明时先核对订单，不重发；订单已创建后停止尝试其他选择 |
| 7. 支付准备与支付结果核对 | 识别已创建订单、支付剩余时间、支付渠道和最终金额；进入官方支付页面；核对成功、失败、取消和订单状态 | 人工付款后能确认订单与支付状态一致；支付跳转或返回不明时接管，不把点击成功当作付款成功 |
| 8. 可选支付自动化研究 | 逐个验证官方支付渠道，研究在明确授权下自动推进可适配步骤；保持显式启用、默认关闭 | 必须限定到确认过的订单、渠道和最终金额；3-D Secure、短信验证、银行确认或未知步骤交给本人。**不能承诺所有支付渠道都能无人值守完成付款** |

按最新指定先完成 JJ 普通票的正常入场、选座和锁座观察，再接入未支付订单；Play＆Stay 套餐另行适配。支付自动化放在订单流程稳定、支付渠道被实际验证之后，单独评估和启用。

选票“不设价格上限”是选择规则，**不等于授权扩展对任意金额自动扣款**。未来支付模块仍需本人明确授权对应订单的最终金额；密码、登录令牌和支付信息不进入扩展长期存储。当前请求只规划付款能力，没有启用或执行付款。

## 全流程任务与恢复设计

后续适配器需要提供“观察页面 → 读取实际可选项 → 选择并确认 → 核对下一步结果”的能力。任务状态将覆盖官方入口、人工验证、排队、场次、库存选择、锁定、资料、订单、支付准备和结果确认；这些是拟开发状态，目前尚未全部实现。

运行状态要分别保存“已选择”“官方确认已锁定”“已创建订单”和“已确认支付”，不能合并为一个成功状态。锁定到期、页面切换、网络中断和提交结果不明时，先通过官方页面确认现状，再决定继续或人工接管；不自行假定成功，也不重复创建订单。

售罄时按保存顺序考虑下一购票选择。锁定成功、订单已创建或支付处理中，应停止尝试其他选择；若需释放并换选，先确认官方释放结果。金额或必要费用未知时仍需核对，取消预算上限不改变这一点。

## 验收与仍需的页面证据

- 模拟场景：触发时间、隐藏 / 休眠、重复触发、首选售罄、库存冲突、部分锁定、锁定到期、验证码中断、页面变化、订单提交超时、支付返回不明。
- 真实页面：先取得已登录且完成所需认证的官方售票会话，以及明确的商品、场次、套餐 / 座区、数量和联系人；目前尚缺这些后段的实际操作证据。
- 已授权实验：生成一次未支付订单，并在付款前停止。当前尚未完成这项真实实验；支付执行授权不包含在这项实验中。
- Chrome 与 Edge 分别验收：不提前进入、不重复进入、不选错配置；锁定、订单和支付状态以官方确认结果为准。记录前台触发耗时，但入场和排队耗时由网站决定。

## 安装与使用

1. 下载并解压仓库源码。
2. 打开 `chrome://extensions` 或 `edge://extensions`，开启开发者模式。
3. 点击“加载已解压的扩展”，选择本仓库的 `extension` 文件夹。
4. 打开扩展“设置”，添加联系人和购票任务。

详细说明见 [中文安装与使用说明](extension/README.md)。

## 源码与验证

`extension/` 包含配置界面、任务状态管理、前台计时、网站适配器及测试。联系人和任务保存在本机扩展存储中；仓库不包含个人浏览器配置或实际联系人数据。`entry-api.js` 由后台通过 `chrome.scripting` 在当前 NOL 商品页的 `MAIN` 环境执行；使用同源 Cookie，不提取登录令牌。验证码及入场凭据只在页面内存中消费，不进入扩展存储、消息或诊断。官方跳转地址包含必要的入场凭据，只用于该次正常跳转。

在仓库根目录运行：

```powershell
node --test extension/tests/*.test.js
```

v0.1.4 的 68 项 Node 测试通过，新增验证预选档位不匹配时不能参与选择或通过订单校验。v0.1.3 的 Edge / Chrome for Testing 20 个隔离场景验证已通过；v0.1.4 未修改页面界面与入场流程，没有重复浏览器验收。覆盖只读官方时间、时区 / 预售类型、忽略伪造或旧手动时间、官网变更复核、接口失败暂停、一次 API 请求、无 DOM 点击、验证取消和未知响应不重试。测试使用公开匿名响应、Turnstile 测试替身和模拟官方入场接口；不会登录、加入真实队列、锁座、下单或支付。本地触发延迟分别为 Edge 60 ms、Chrome 93 ms，不是服务器入场或排队耗时保证。

v0.1.5 的 85 项 Node 测试通过，补充准确入场错误保留、取消后恢复、晚到回执、导航错误过滤、当前标签匹配及凭据不持久化的回归验证。Edge / Chrome 各 9 项弹窗状态检查通过，控制台和外发请求均为零。隔离 Edge 中一次本机中止导航产生了真实 webNavigation 错误事件，后台正确转为人工接管且没有重发 API；Chrome 的同类导航实验状态未稳定，尚未通过验收，不能承诺每次错误都能识别。可复用脚本为 `extension/tests/popup_state_smoke.py`，实际事件实验需显式启用 `--real-navigation`。真实网络超时只确认了官网入口后阻塞，不能代替后段流程验收。
